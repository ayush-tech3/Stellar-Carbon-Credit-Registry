The Problem

Carbon credit markets are broken. Traditional registries suffer from fraud, double-spending, and lack of transparency. Companies buy and sell carbon credits to offset their climate impact, but there's no public audit trail of the credit lifecycle.

Our Solution

CarbonTrack builds a transparent, tamper-proof registry on the Stellar blockchain that manages the full lifecycle of carbon credits:

🌱

Issue

Verified organizations mint new carbon credits from real projects like reforestation, solar energy, and direct air capture.

🔄

Transfer

Companies buy, sell, and trade credits — all tracked on-chain with full provenance and audit trail.

🔥

Retire

When a company claims its offset, the credit is permanently burned — can never be reused. Double-spending is cryptographically impossible.

Why Stellar & Soroban?

⚡ Low Transaction Costs

Stellar's fee model keeps carbon credit operations affordable at scale — typically < $0.01 per transaction.

🌐 Global Accessibility

5-second finality means credits can be issued, transferred, and retired in near real-time worldwide.

🔒 Cryptographic Security

Soroban smart contracts enforce business rules on-chain, making double-spending mathematically impossible.

🌍 Environmental Sustainability

Stellar's consensus mechanism uses minimal energy — fitting for a climate-focused application.

Get CarbonTrack running locally in under 10 minutes.

Install →

Step 1 — Clone the Repository

Terminal 
git clone https://github.com/ayush-tech3/Stellar-Carbon-Credit-Registry.git
cd Stellar-Carbon-Credit-Registry

Step 2 — Build Smart Contracts

Terminal 
cd contracts
rustup target add wasm32-unknown-unknown
cargo build --release --target wasm32-unknown-unknown -p retirement-manager
cargo build --release --target wasm32-unknown-unknown -p carbon-credit-registry
cargo test --workspace

Step 3 — Deploy to Stellar Testnet

Terminal 
# Generate a testnet identity (funded automatically)
stellar keys generate deployer --network testnet --fund

# Run the deployment script
chmod +x scripts/deploy-testnet.sh
./scripts/deploy-testnet.sh
The deployment script will output contract addresses. Save them for the frontend configuration.

Step 4 — Setup Frontend

Terminal 
cd frontend
cp ../.env.example .env.local
# Edit .env.local with your contract addresses

npm install
npm run dev

Open http://localhost:3000 and connect your Freighter wallet to start interacting with the registry.

Step 5 — Run Tests

Terminal 
# Smart contract tests
cd contracts && cargo test

# Frontend tests
cd frontend && npm run test -- --run

📜 Smart Contract Design

Two Soroban smart contracts work together to manage the full carbon credit lifecycle.

Contract 1: CarbonCreditRegistry

The core registry that manages issuance, transfer, and initiates retirement of carbon credits.

carbon_credit_registry Core Contract

Key Responsibilities

  • Manage admin and authorized issuers (RBAC)
  • Mint new carbon credit batches with project metadata
  • Transfer credits between addresses with balance validation
  • Initiate retirements via cross-contract call to RetirementManager
  • Emit events for all state changes

Storage Patterns

  • Instance Storage: Admin address, retirement contract address, next credit ID
  • Persistent Storage: Credit info, balances, issuer authorizations

Contract 2: RetirementManager

Immutable retirement ledger with global CO₂ offset tracking.

retirement_manager Retirement Ledger

Key Responsibilities

  • Record permanent retirement entries (called only by Registry)
  • Track global CO₂ tons retired across all users
  • Provide query access to retirement records by owner or ID
  • Maintain immutable audit trail

Security Model

  • Caller Validation: Only accepts calls from the registered registry contract
  • Immutability: Once recorded, retirements cannot be reversed

Inter-Contract Communication

When a user retires credits, the Registry contract atomically deducts the balance and calls the RetirementManager to create a permanent record. This cross-contract design ensures:

🔗 Atomic Operations

Balance deduction and retirement recording happen in one transaction — if either fails, both revert.

🛡️ Trust Boundary

RetirementManager only accepts calls from the Registry, preventing unauthorized retirement records.

Data Types

types.rs — CreditInfo
#[contracttype]
#[derive(Clone, Debug)]
pub struct CreditInfo {
    pub id: u64,           // Unique credit batch ID
    pub issuer: Address,   // Address of the authorized issuer
    pub project: String,   // Project name (e.g., "Amazon Reforestation")
    pub amount: i128,      // Total credits issued in this batch
    pub retired: i128,     // Total credits retired from this batch
    pub vintage: u32,      // Vintage year (e.g., 2024)
    pub method: String,    // Methodology (e.g., "VCS", "Gold Standard")
    pub active: bool,      // Whether the credit batch is active
}
types.rs — RetirementRecord
#[contracttype]
#[derive(Clone, Debug)]
pub struct RetirementRecord {
    pub id: u64,           // Unique retirement record ID
    pub credit_id: u64,    // Reference to the credit batch
    pub owner: Address,    // Who retired the credits
    pub amount: i128,      // Amount of tCO₂ retired
    pub project: String,   // Project name
    pub vintage: u32,      // Vintage year
    pub timestamp: u64,    // Block timestamp of retirement
}

🔒 Security

Security-first design across smart contracts, frontend, and operations.

Smart Contract Security

🛡️

Access Control

All privileged functions gated by Address.require_auth() plus stored admin/issuer checks. Separate admin and issuer roles enforce principle of least privilege.

🔐

Double-Spend Prevention

Credits are atomically deducted before retirement — balance can never go negative. Checked arithmetic prevents overflow exploits.

🔗

Cross-Contract Trust

RetirementManager only accepts calls from the registered registry contract address, preventing unauthorized retirement records.

✅

Input Validation

All amounts must be > 0, credit IDs must exist, addresses must be valid. Comprehensive validation at every entry point.

⬆️

Upgrade Safety

Only admin can upgrade contracts. WASM hash is validated by the Soroban host environment.

📦

No Unbounded Growth

Storage keys are structured to prevent DoS via unbounded data. Each key has a defined scope and lifetime.

Frontend Security

✅ No Private Keys — All signing done via Freighter wallet extension
✅ Environment Variables — Sensitive values in .env.local, never committed
✅ Input Sanitization — All user inputs validated before contract calls
✅ Error Boundaries — Graceful error handling prevents information leakage
✅ HTTPS Required — Wallet extensions require secure context

Operational Security

✅ Immutable Retirement — Once retired, credits cannot be un-retired
✅ Audit Trail — All state changes emit events, queryable via Soroban RPC
✅ Upgrade Mechanism — Contracts can be patched without redeployment

💻 Frontend Guide

The frontend is built with Next.js 15 using the App Router, TypeScript, and a feature-based module architecture.

Architecture Pattern

Feature-Based Module Architecture: Each feature (credits, retirement, activity, transactions, analytics) is self-contained with its own components, hooks, and services. No blockchain logic exists directly in UI components — everything goes through the service layer.

State Management

🔄 Server State (React Query)

All blockchain data fetching uses TanStack React Query v5 for automatic caching, refetching, and background updates. Credit balances, activity events, and transaction status are all managed this way.

📦 Client State (Zustand)

Local UI state like wallet connection, portfolio data, transaction queue, event feed, settings, toast notifications, and feedback data use Zustand stores with optional localStorage persistence.

One-Command Deployment

stellar keys generate deployer --network testnet --fund

# Deploy both contracts + initialize + register issuer
./scripts/deploy-testnet.sh
